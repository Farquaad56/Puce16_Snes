# E09-00 - TUNE: sprites decales d'une ligne (SMW: debris colores sur la ligne 0 en haut de l'image) - reporte apres la v1
Epopee: E09 | Type: code | Dependances: E08-39 | Taille estimee: ~60 lignes

## Contexte
Bug trouve au GATE E07-14 (SMW, ecran de niveau et carte), accepte comme defaut connu et reporte ici a la demande de l'utilisateur (le gate E07-14 peut etre approuve sans ce correctif): de petits debris colores (vert, rouge, orange, blanc) apparaissent sur la toute premiere ligne de l'image (ligne de sortie 0, x environ 90 a 135). Diagnostic fait par Claude (non a deviner): SMW cache ses sprites inutilises en mettant Y=240 (OAM $F0, taille petite = 16x16 avec OBSEL de SMW). `crates/puce16-core/src/ppu/obj.rs` calcule la rangee du sprite avec `row = (r - y - 1) & 0xFF` (dans `sprite_list` ET dans `render_obj_line`, spec 05b section 6.2 ligne `row = (r - y - 1) & 0xFF`, avec `r` = ligne de sortie 0..223). Avec cette formule un sprite 16x16 a Y=240 couvre r=241..256, donc la rangee 15 revient se dessiner sur r=0: c'est l'artefact. Sur la console un sprite a Y=0 commence sur la premiere ligne visible (l'evaluation des sprites de la ligne v se fait pendant la ligne v-1, donc rangee = `(r - y) & 0xFF`, le « +1 » de la doc materielle est deja absorbe par `r = v - 1`). Experience faite en local puis ANNULEE: avec `row = (r - y) & 0xFF` dans les deux fonctions, la ligne 0 de SMW est propre (seule la colline de fond reste), mais ~30 tests e05_ changent car ils ont ete ecrits avec l'ancienne formule: `e05_10_row_visibility_y255`, `e05_10_row_visibility_y0`, `e05_10_large_height`, et la plupart des tests de `e05_11_sprite_pixels.rs` (ils utilisent y=255 comme « premiere rangee visible »), ainsi que le helper de `e05_14_pick.rs` (ligne 414).
Cette tache est donc une CORRECTION DE SPEC approuvee par la gate: la spec 05b et les tests e05_ qui l'encodent doivent etre alignes sur le comportement materiel. Ce n'est pas un affaiblissement de test: chaque test garde son intention (visibilite, hauteur, flips, limites 32/34), seul le Y utilise est decale d'une unite.

## Specification
1. Reproduire (l'option `--input` du CLI est deja disponible): `cargo run --release -q -p puce16-cli -- run tests/roms/games/smw.sfc --frames 1500 --input "700-705:start,800-805:a,900-905:a,1000-1005:a,1100-1105:a,1200-1205:a,1300-1305:a" --dump-ppm tests/out/e09_00_smw.ppm`. Avant correction, la ligne 0 de l'image contient des pixels non fond (x 90..135) en plus de la colline bleue (x >= 151). L'exemple `cargo run --release -p puce16-core --example smw_oam -- tests/roms/games/smw.sfc 1500` liste les sprites a Y=240 responsables.
2. Corriger `obj.rs`: `row = ((r as i32) - (s.y as i32)) & 0xFF` dans `sprite_list` ET dans `render_obj_line` (les deux doivent rester identiques; en faire une petite fonction commune `sprite_row(r, y)` pour qu'elles ne divergent plus).
3. Mettre a jour la spec 05b: section 6.2 (formule et commentaire: `Y = 0` -> premiere rangee visible, `Y = 255` -> la rangee 1 du sprite sur la ligne 0, un sprite 16x16 a `Y = 240` n'atteint PAS la ligne 0, un sprite de hauteur 32 ou 64 deborde bien par le haut), et la ligne 240 (liste des tests: remplacer `Y=255 visible a la rangee 0; Y=0 non visible a la rangee 0` par la nouvelle regle). Ajouter une ligne d'historique dans la spec indiquant que la formule a ete corrigee par E09-00 et pourquoi (SMW cache ses sprites a Y=240).
4. Mettre a jour les tests e05_10, e05_11 et e05_14: decaler le Y des sprites de test d'une unite (255 -> 0 pour « premiere rangee visible », etc.) et ajuster les attentes de visibilite. Chaque test garde sa signification d'origine; ne supprimer aucune assertion. Si un test devient impossible a adapter sans en changer le sens, question bloquante (`docs/qa/inbox`).
5. Test de non-regression `e09_00_*` (nouveau fichier) avec valeurs concretes, qui ECHOUE avant la correction: sprite 16x16 a Y=240 invisible sur la ligne 0 (et sur toutes les lignes 0..223); sprite 8x8 a Y=0 visible sur les lignes 0..7 avec rangee = ligne; sprite 32x32 a Y=240 visible sur les lignes 0..15 (rangees 16..31).
6. Relancer la suite: `target/release/puce16-cli suite tests/manifest.toml`. Les ROM avec sprites changeront de hash (decalage d'une ligne): regarder les images `tests/out/suite/*.ppm` des ROM de sprites avant de refiger, puis `--update-baseline <nom>` pour chacune. Noter dans `docs/qa/SUITE_REPORT.md` la liste des ROM re-figees. Si une ROM de test sprite (ex: celles de E05) devient fausse visuellement, STOP et question bloquante: la formule est alors a reconsiderer.
7. Fin de tache: la ligne 0 de la capture SMW ne contient plus de debris (voir `accept`). L'utilisateur reverifie SMW dans le desktop apres la correction.

## Tests
Tous les tests sont prefixes par `e09_00_`.

- `e09_00_sprite_16x16_y240_hidden_on_all_rows` : 16x16 a Y=240: aucune ligne de sortie 0..223 ne contient le sprite (regression SMW)
- `e09_00_sprite_y0_first_visible_row` : 8x8 a Y=0: visible sur les lignes 0..7, ligne 0 = rangee 0
- `e09_00_sprite_32x32_y240_wraps_to_top` : 32x32 a Y=240: visible sur les lignes 0..15 avec les rangees 16..31 (debordement materiel)
- `e09_00_sprite_list_and_render_use_same_row` : sprite_list et render_obj_line donnent la meme rangee pour tous les Y de 0 a 255
